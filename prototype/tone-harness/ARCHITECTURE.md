# 말투 알림 채팅 앱 시스템 구조 (수업 프로젝트용)

1:1 채팅 앱 안에서, 내가 보내려는 문장이 상대에게 차갑거나 성의 없게 읽힐 수 있을 때 나에게만 조용히 알려 주는 서비스다. 채팅은 우리 앱이 직접 만들고, 그 안에 말투 하네스(레이어 네 개 + 여러 LLM)를 붙인다.

기준은 수업 데모와 팀원·지인 20~30명 정도의 짧은 파일럿이다.

## 1. 왜 채팅 앱을 직접 만드나

카카오톡이나 인스타그램 개인 대화에는 외부 서비스가 들어갈 공식 방법이 없다. 우리 앱 안에서는 이 문제가 한 번에 풀린다.

| 필요한 것 | 우리 채팅 앱에서는 |
|---|---|
| 보내기 전 문장 보기 | 입력창이 우리 것이라 바로 볼 수 있음 |
| 대화 맥락 | 대화가 우리 DB에 있어서 서버가 직접 꺼내 씀 |
| 나에게만 보이는 알림 | 보낸 사람 화면에만 힌트를 보냄 |
| 상대의 숨은 피드백 | 받은 메시지를 길게 눌러 AI에게만 털어놓는 기능을 직접 만듦 |
| 동의 | 두 사람 모두 가입할 때 '말투 도움' 이용에 동의 |

## 2. 구성 요소

```
┌──────────────┐  WebSocket·REST   ┌──────────────────────── API 서버 (FastAPI) ────────────────────────┐
│ 채팅 앱       │ ────────────────▶ │  채팅 처리        말투 하네스 (L0~L3, 고쳐 쓰기)     피드백 처리 (L4) │
│ (웹 / 앱)     │ ◀──────────────── │  저장·전달        실시간·상세 경로                  비동기 작업      │
└──────────────┘  메시지, 나만의 힌트 └──────┬───────────────────┬────────────────────────────┬─────────┘
                                          │                   │                            │
                                   ┌──────▼──────┐     ┌──────▼───────────┐         ┌──────▼──────┐
                                   │ 채팅 DB      │     │ 모델 공급자        │         │ 패턴 저장소   │
                                   │ (SQLite)     │     │ NVIDIA·Gemini·    │         │ (관계·전체)   │
                                   │ 대화·이벤트   │     │ GitHub·로컬 vLLM  │         │ 원문 없음     │
                                   └─────────────┘     └──────────────────┘         └─────────────┘
```

| 구성 요소 | 하는 일 | 수업용 선택 | 나중에 바꿀 수 있는 것 |
|---|---|---|---|
| 채팅 앱 | 1:1 대화, 입력 중 힌트, 살펴보기 시트, 털어놓기 시트 | HTML 한 장 (`server/static/index.html`) | React Native(Expo)나 Flutter 앱 |
| API 서버 | WebSocket으로 메시지·힌트 전달, REST로 살펴보기·털어놓기·이벤트 | FastAPI 한 프로세스 | 채팅과 하네스를 다른 프로세스로 분리 |
| 말투 하네스 | 레이어 호출, 모델 폴백, 한도, 시간 제한 | 서버 안에서 같이 돔 | 별도 워커 |
| 피드백 처리 | 하소연 → 패턴, 원문 삭제 | 서버 안의 비동기 작업 | Redis 큐 + 워커 |
| 채팅 DB | 사용자, 방, 메시지, 측정 이벤트, 피드백 기록 | SQLite 파일 | PostgreSQL(Supabase 등) |
| 패턴 저장소 | 관계별 패턴, 전체 패턴, 내 평소 말투 기준선 | JSON 파일 | DB 표로 이동 |
| 모델 공급자 | 실제 LLM | NVIDIA 무료, Gemini 무료, 로컬 SEED | 유료 API, 자체 서버 |

## 3. 흐름

### 입력 중 (실시간 경로, 1.5초)
1. 입력이 0.5초 멈추면 앱이 `draft`(방 ID, 문장, 순번)를 WebSocket으로 보낸다.
2. 서버가 DB에서 최근 대화 8개를 꺼내 맥락을 만든다. 앱이 보낸 맥락은 쓰지 않는다.
3. L0 거르기 → (의심되면) L1·L2 동시 호출 → L3 계산식.
4. 결과는 보낸 사람에게만 `hint`로 간다. 그사이 새 입력이 왔으면 이 결과는 버린다.
5. 1.5초를 넘기거나 모델이 모두 실패하면 아무것도 보내지 않는다.

### 전송
1. `send` → DB 저장 → 두 사람에게 `message`.
2. 힌트가 떠 있어도 전송은 막지 않는다. 고칠지는 본인이 정한다.
3. 보낸 문장으로 내 평소 말투 기준선(길이, 존댓말 비율, ㅎㅎ 비율)만 갱신한다.

### 살펴보기 (상세 경로, 8초)
힌트의 "살펴보기"를 누르면 `POST /api/tone/detail`. 큰 모델로 다시 읽고, 다른 회사 모델로 두 번째 의견을 받고, 갈리면 심판 모델에 묻는다. 고쳐 쓴 문장은 의도·말투·오해 감소 확인을 통과한 것만 보여 준다. 내부 판단 근거(점수 계산 내용)는 앱으로 내보내지 않는다.

### 털어놓기 (비동기)
1. 받는 사람이 받은 메시지의 "⋯"를 눌러 하소연을 쓴다. 상대에게는 보이지 않는다.
2. 서버는 그 메시지가 정말 받은 메시지인지 확인한 뒤, 메시지 내용과 하소연을 함께 L4에 넘긴다. 어떤 표현에 대한 불편함인지 알 수 있어서 자유 서술보다 패턴이 정확해진다.
3. 패턴 태그만 저장하고 원문은 버린다. DB에는 '언제, 어느 방에서, 쓸 만했는지'만 남는다.
4. 털어놓은 사람에게도 무엇이 추출됐는지는 보여 주지 않는다.

## 4. API와 WebSocket

| 종류 | 경로 | 보내는 것 | 받는 것 |
|---|---|---|---|
| WS | `/ws/{user_id}` → `draft` | room_id, text, seq | 보낸 사람에게만 `hint` (seq, hint 또는 null) |
| WS | `/ws/{user_id}` → `send` | room_id, text | 두 사람에게 `message` |
| REST | `POST /api/tone/detail` | room_id, user_id, text, intent | readings, why, options, footnote |
| REST | `POST /api/feedback` | room_id, user_id, message_id, text | ack 문구만 |
| REST | `POST /api/events` | kind, choice 등 | ok |
| REST | `GET /api/rooms`, `GET /api/rooms/{id}/messages` | user_id | 방 목록, 메시지 |
| REST | `GET /api/stats/{user_id}` | | 알림 수, 살펴보기 수, 고친 수, 고친 비율 |
| REST | `POST /api/users/{id}/hint?on=` | | 힌트 켜기/끄기 |

모든 요청에서 그 사용자가 방 참여자인지 확인한다.

## 5. 데이터 모델

| 표 | 주요 칸 | 메모 |
|---|---|---|
| users | id, name, tone_hint_on | 힌트 끄기 설정 |
| rooms | id, user_a, user_b, relation | 1:1 방 하나 = 관계 하나(pair_id) |
| messages | id, room_id, sender_id, text, created_at | 채팅 앱이라 저장 |
| tone_events | room_id, user_id, kind, risk, top_reading, signals, choice | 측정용. 문장 원문 없음 |
| feedback_log | room_id, reporter_id, message_id, usable, pattern_count | 하소연 원문 없음 |
| 패턴 저장소 | 관계별 태그·횟수·강도, 전체 태그 수, 사용자별 기준선 | 지금은 JSON 파일 |

## 6. 앱 쪽 규칙

- 0.5초 디바운스, 요청마다 순번을 붙이고 최신 순번의 힌트만 표시한다.
- 힌트는 입력창 바로 위에, 확정하지 않는 말투로만 보여 준다.
- 힌트가 떠 있어도 보내기 버튼은 항상 살아 있다.
- 받은 메시지에만 "⋯ AI에게만 털어놓기"가 있다.
- 측정 이벤트를 남긴다: `hint_shown`, `detail_opened`(서버), `option_chosen`(A/B/그대로), `sent_with_hint`, `sent_after_fix`(힌트가 떴다가 고친 뒤 사라진 상태로 보냄).

## 7. 말투 하네스 레이어

| 레이어 | 하는 일 | 모델 |
|---|---|---|
| L0 거르기 | 겉 신호와 상대 말의 무게(감정, 초대, 소식, 사과)를 보고 LLM을 부를지 정함 | 없음(규칙) |
| L1 맥락 | 상대 직전 말의 의도와 기대할 답의 모양 | 실시간: DeepSeek V4.1 Flash / 상세: Kimi K3 |
| L2 말투 | 읽힘을 분포로 냄 | 실시간: HyperCLOVA X SEED 1.5B(로컬) / 상세: SEED Think 14B + Gemini Flash |
| L3 판단 | 계산식으로 합침. 갈리면 심판 또는 기권 | 계산식, 심판은 Kimi K3 |
| L4 피드백 | 받은 메시지 + 하소연 → 패턴 태그 | Kimi K3 |
| 문구 검사 | 확정 표현, 출처 노출 막기 | 템플릿 + 금지어 |

```
위험도 = sigmoid( w0 + w1 × L0 사전점수 + w2 × L2 부정 읽힘 확률
               + w3 × 기대 어긋남 + w4 × 관계 패턴 일치 )
```

- 두 말투 판단의 차이가 0.35를 넘거나 확신이 낮으면 기권한다.
- 알림 기준값은 평가 세트에서 정밀도 0.8 이상이 나오는 값.
- 관계 패턴 점수는 전체 패턴에도 같은 신호가 충분히 쌓였을 때만 더한다. 한 사람의 하소연만으로는 알림이 뜨지 않고, 화면 문구 "비슷한 대화에서 모인 반응"도 사실이 된다.
- 같은 계열 모델은 실수도 비슷해서 L2 두 의견은 다른 회사 모델로 짝짓는다.
- HyperCLOVA X 라이선스에 AI 출력물을 사람이 쓴 것처럼 내놓는 걸 막는 조항이 있어 분석에만 쓰고, 고쳐 쓰기는 DeepSeek이 한다.

## 9. 하네스 부품

| 부품 | 역할 |
|---|---|
| 라우터 | 역할 이름으로 모델 목록을 찾고 앞에서부터 시도, 실패하면 다음 |
| 한도 관리 | 공급자·모델별 토큰 버킷 |
| 차단기 | 같은 모델이 3번 연속 실패하면 60초 건너뜀 |
| 시간 제한 | 실시간 1.5초, 상세 8초, 비동기 60초 |
| 스키마 검사 | pydantic. 깨지면 다음 모델, 모두 실패하면 기권 |
| 캐시 | 같은 문장·맥락이면 재사용 |
| 개인정보 가리기 | 외부 API 전송 전 전화번호, 이메일, 긴 숫자 |
| 호출 기록 | 역할, 모델, 지연, 성공 여부. 원문 없음 |

모델 이름은 `config/models.yaml`에만 있다. 키가 없으면 mock 모델로 떨어져서 API 없이도 채팅 데모 전체가 돈다.

## 10. 한도 계산 (파일럿 기준)

- 거르기 통과 비율을 10%로 가정. 실시간 경로는 통과한 메시지당 외부 호출 1~2번.
- NVIDIA를 모델당 분당 40회로 잡으면 DeepSeek 하나로 전체 메시지 분당 400개 정도. 30명 파일럿엔 충분하다.
- 무료 API는 응답 속도가 들쭉날쭉하다. 1.5초를 넘기면 그 메시지는 힌트 없이 지나가므로, 데모 때는 L2를 로컬 1.5B로 두는 게 안정적이다.

## 11. 고른 것과 포기한 것

| 결정 | 얻는 것 | 잃는 것 |
|---|---|---|
| 채팅 앱을 직접 만듦 | 맥락·숨은 피드백·나만의 힌트를 모두 구현 가능 | 사람들이 원래 쓰던 메신저가 아님 |
| 서버 한 프로세스 | 만들기 쉽고 시연이 간단 | 사용자가 많아지면 분리 필요 |
| 세 경로 분리 | 실시간 응답, 한도 절약 | 실시간 판단은 덜 정확 |
| 전송을 막지 않음 | 사용자가 판단 주체로 남음 | 힌트를 무시할 수 있음 |
| 계산식 앙상블 | 설명 가능, 데이터로 가중치 조정 | 처음엔 손으로 정해야 함 |
| 하소연 원문 미저장 | 개인정보 부담 감소 | 나중에 다시 분석할 수 없음 |

## 12. 수업 일정에 맞춘 단계

| 단계 | 만들 것 | 확인할 것 |
|---|---|---|
| 1 | 채팅 서버 + 웹 앱 + mock 하네스 (지금 상태) | 두 화면에서 대화, 힌트, 살펴보기, 털어놓기가 도는지 |
| 2 | 실시간 경로에 DeepSeek, L2에 SEED 1.5B 연결 | 1.5초 안에 나오는지 |
| 3 | 대조 세트 30쌍 + 평가 | 정밀도, 기권률, 맥락에 따라 판단이 갈리는지 |
| 4 | 상세 경로 실제 모델 연결 | 고쳐 쓴 문장이 의도와 말투를 지키는지 |
| 5 | 털어놓기 → 패턴 → 다음 대화 반영 | 같은 패턴에 힌트가 뜨는지 |
| 6 | 1주 파일럿 (tone_events로 측정) | 알림 수 변화, 고친 비율, 알림 전 스스로 고친 문장 |

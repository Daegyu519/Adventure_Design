## 생각의 흐름

### 1. 라벨 결과: 사람은 맥락보다 "문장 자체 + 관계"로 판단했다

- 날카로운 말("알아서 하세요", "신경 꺼", "바빠", "별로")은 무난한 맥락에서도 5/5. → 평균이 곧 답인 구간.
- 무난한 말은 아픈 맥락에서도 안 걸림: 면접 떨어진 친구에게 "괜찮아" 0/5, 휴학 상의하자는 아빠에게 "알았어" 0/5. → 말투가 아니라 **내용이 상대 기대에 어긋난** 경우. 11/10의 "뭐라고 답하지" 가설과 같은 방향.
- 3:2 15개에는 정당한 거절("그건 어렵습니다", "다음에요", "내가 알아서 할게")이 몰려 있다. 여기서 경고하면 과잉 순화.
- 관계별 경고(다수결): 가족 8/10, 연인 7/10, 직장 3/10.
- 라벨러별: 관계 위주로 이유를 쓴 사람은 L1·L4(둘 다 프로젝트를 아는 팀원). 맥락에 따라 실제로 판단을 가장 많이 바꾼 사람은 L3(10쌍), 가장 적게 바꾼 사람은 L2(4쌍).
- 한계: 라벨러는 **제3자**다. "실제 수신자에게 맥락·기억이 중요하지 않다"는 결론이 아니다. 당사자의 서운함은 하소연 데이터로만 확인된다. 5명 중 2명이 팀원.

### 2. LLM 라벨러(Codex)

- 일치 수준은 보통 사람 한 명. 하지만 **틀리는 방향이 정해져 있다**: 다수결과 다른 12개 중 10개가 "사람은 다 걸렀는데 Codex는 통과"(지침의 '단순 확인·정당한 거절은 괜찮음'을 문자 그대로 적용). 반대로 기념일에 "고마워"는 사람 2/5인데 Codex는 걸렀다.
- 정리: **LLM은 맥락·상대 기대로, 사람은 말 자체·관계로** 판단. LLM이 다르게 보는 곳이 오히려 사람이 놓치는 곳(B 영역)일 수 있다.
- 쓰는 법: 보조 라벨러로는 가능, 최종 평가 기준은 사람 라벨. LLM 라벨로 평가하면 모델이 사람이 아니라 LLM 취향에 맞춰진다.

### 3. 머신러닝 현황: 사실상 "Qwen을 흉내 내는 분류기"

- 머신러닝이 쓰이는 곳 셋: ① LLM 판단(Qwen3-30B 등, 학습 안 함·프롬프트만) ② **KcELECTRA 분류기(유일하게 직접 학습)** ③ 집계 가중치(사람이 손으로 정함, T-20 미실시).
- 분류기 경과: P-14 규칙 약지도 234행 → 전부 0 예측(실패). P-14b **Qwen3-30B가 선생님**으로 AI-Hub 공감형 대화 6,000행에 라벨(40%는 고정 문구로 바꾼 변형) → 선생님 일치 88%, 대조 16문장에서 정밀도 최대 0.75로 기준 미달. P-28 사용자 결정으로 집계 가중 항(clf 2.0)에 연결.
- 단계: 데이터 ✅ → 라벨(LLM) ✅ → 학습 ✅ → **사람 기준 평가 ❌(건너뜀)** → 운영 연결 ✅. 이번 라벨로 건너뛴 단계로 돌아갈 수 있게 됐다.
- 데이터 한계: 원문은 실제 구어체지만 공감 대화 수집용이라 메신저식 비정형 표현(ㅋ, 하셈, ㅇㅇ)이 얼마나 있는지 미확인(학교 서버 `/root/p14b`).

### 4. 결정성: 같은 텍스트·같은 맥락이어도 결과가 다를 수 있다

- 라우터 메모리 캐시(같은 요청은 엔진이 켜져 있는 동안 같은 답, 재시작·캐시 비움 뒤엔 새로 물음).

### 5. 본질 질문 다시: 이 모델은 뭘 잡아야 하나

| 유형 | 사람이 알아채나 | 도구가 필요한가 |
|---|---|---|
| 날카로운 말 | 5/5로 알아챔 | 거의 불필요(보내는 사람도 앎). 겉 신호·분류기로 충분 |

- 라벨링 질문도 바꿔야 할 수 있다: "알려 줄 만한가"(제3자) → "이 말을 받는 사람이라면 서운할까"(수신자).

### 6. 아이디어(획기적인 방식 후보, 미결정)

1. **"차가운가"가 아니라 "내 의도대로 읽히나"**: 의도(단호/부드럽게/위로 등)를 고르면, 예상 읽힘이 의도와 어긋날 때만 알림. 엔진에 의도 칩·`render_mismatch`가 이미 있음.
2. **비교 판단**: "이게 차가운가?"(갈림) 대신 "A와 B 중 어느 쪽이 더 서운한가?"(잘 일치한다고 알려짐). 시안 B(답장 후보 비교)와 연결. **2주 안에 해 볼 수 있는 1순위.**
3. **정답 대신 "불편해할 사람 비율"**: "5명 중 4명은 서운할 수 있어요 + 이유". 5명 득표 비율이 예측 목표가 된다. 감정 5개 정형화의 대안.

### 7. 비정형 표현(어미·꼬리) 변형 세트 제안

- 지금 60문장은 전부 표준어. 실제 메신저에서는 "알아서 하세요." / "알아서 하세요ㅎㅎ" / "알아서 하셈 ㅋ" / "알아서해~"가 전혀 다르게 읽힌다.

# 11/14 추가 (다른 세션): 방향 논의와 엔진 문제점 목록

## 9. 논의 정리

**"다른 AI 기업은 평균 수렴·사람다움을 어떻게 풀었나"에 대해**
- 기업들의 메모리는 "나와 대화하는 사용자"를 기억한다. 우리는 "대화에 없는 제3자(수신자)의 반응"을 예측해야 해서 그대로 가져올 수 없다. 대신 수신자 반응 데이터(하소연)는 우리 쪽에만 있다.
- 평균은 범용 레이어에서는 결함이 아니다. 처음 보는 상대에게는 평균이 최선이다. 범용 판정 = 사전 확률, 패턴·습관 = 그 위의 보정.
- "서운함 0"을 목표로 두면 정당한 거절까지 순화하게 된다. 그대로 보내기(재분석 없음)가 이를 막는 장치.
- 인용된 자료 중 2026년 것(OpenAI Dreaming, Anthropic 메모리 글, CHI 연구, Beyond Consensus)은 원문 미확인. 보고서에 쓰려면 직접 확인.

**욕설과 맥락 ("친구에겐 별 의미 없을 수도, 맥락에 따라 싸해질 수도")**
- "욕설이면 항상 알림"은 틀린 설계. 고칠 것은 맥락을 보느냐가 아니라 **맥락을 무엇으로 보느냐**다. 지금은 LLM 한 개가 매번 새로 판단해서 흔들린다.
- LLM 없이 셀 수 있는 신호: ① 이 사람(이 사이)의 평소 욕설 비율 ② 직전 상대 말(ㅋㅋ·장난·상대도 욕 ↔ 사과·서운함·진지함·따짐) ③ 내 문장의 꼬리(ㅋㅋ·~ ↔ 단독·마침표) ④ 관계.
- 세 갈래: 싸한 쪽으로 모이면 모델 없이 알림(결정적) / 장난 쪽이면 알리지 않음 / 섞이면 그때만 LLM, 못 오거나 자신 없으면 알리지 않음.
- ①이 "메모리와 연속성"의 가장 싼 형태다. 기준선(`tone.baselines`: 평균 길이·존댓말 비율·부드러운 표현 비율)에 욕설 비율을 더하는 정도.
- 검증: 지금 60문장에는 장난 욕이 없다. "같은 욕 × 장난 맥락/싸한 맥락" 10~15쌍을 조원에게 물으면 된다(맥락이 실제로 판단을 가르는 구간이라 30쌍 중 7쌍보다 잘 갈릴 것으로 예상, 가설).

**콜드스타트**
- 피할 수 없지만 구간이 짧다: 지금 대화의 직전 몇 턴은 기록 없이도 보인다 / 보내는 사람 습관은 새 상대에게도 따라간다 / 평균은 전체 하나가 아니라 관계별로 시작(라벨: 가족 8/10, 직장 3/10).
- 모를 때는 알리지 않는다(비용이 "틀린 알림"이 아니라 "놓친 알림"이 되게). 개인화는 스위치가 아니라 관찰 수에 따른 비율로.
- 파일럿 규모에서는 대부분의 사이가 끝까지 얕다. 수치로 보일 것은 "관계별 평균 + 지금 대화 + 보내는 사람 습관", 사이별 개인화는 구조와 사례로.

## 10. 같은 말에 알림이 떴다 안 떴다 하는 이유 (코드로 확인, trace는 미확인)

실시간 위험도: `z = -2.2 + 1.6·prior + 2.4·neg (+ 2.0·clf)`, `risk = sigmoid(z)`, 알림은 `risk ≥ 0.6` 즉 `z ≥ 0.405` (`engine/layers/aggregate.py`, `engine/config/models.yaml`).

| 상황 | 알림 조건 |
|---|---|
| 모델(말투 전문가)이 1.35초 안에 못 옴 | **무조건 알림 없음**(기권). prior가 1.0이어도 z = -0.6 |
| 판별기 없음, 겉 신호 없음(prior 0) | 2.4·s ≥ 2.6 → **불가능** |
| 판별기 없음, 욕설(prior 0.35~0.5) | s ≥ 0.75~0.85 → 모델이 0.8/0.9를 오가면 뒤집힘 |
| 판별기 0.9, 겉 신호 없음 | s ≥ 0.34 → 쉽게 알림 |

"시발련아": 정규식이 잡는다(비속어 +0.35, 4글자라 짧은 답 +0.15). 그래도 모델이 제때 와서 s를 높게 줘야 알림. temperature 0.2, 성공한 답만 캐시(시간 초과는 캐시 안 됨)라 "처음엔 안 뜨다가 나중엔 계속 뜨는" 모양이 나온다. 지금은 Mac 임시 운영(실시간 = NVIDIA laguna, 한가할 때 약 1초·부하 때 4~12초, 판별기 꺼짐).

## 12. 배포 문턱과 trace 분포 확인 (11/14, E-09·E-01 실측)

방법: `AGENTS.md` 배포 절, 공개 `/health`, `tone.analysis_traces`의 hint 행 최근 14일 366건(`.env.pilot`, 문장·사용자·방은 읽지 않음). 서버의 `.env.pilot.engine`은 이 PC에 없어 직접 보지는 못했다.

**문턱: 운영 값은 0 / 0.3 / 0.2 (gate / alert / min_confidence)**
- `AGENTS.md` 기록: 2026-11-03 사용자 요청 "민감도 엄청 높여"로 낮춘 값. `models.yaml` 기본은 0 / 0.6 / 0.4. `PATTERN_MIN_OBS`는 1.
- trace와 일치: laguna가 답한 47건 중 위험도 0.3 이상 87% = 실제 알림 87%. Mac 임시 엔진도 같은 env 파일을 쓴다(`scripts/mac-engine`).

**알림 과다: 모델이 답하면 81~87%가 알림**

| 말투 모델 | 답한 건 | 알림 | 문턱 0.45였다면 | 0.6 | 0.7 |
|---|---|---|---|---|---|
| Gemma3-4B (11/01~02) | 101 | 81% | 89% | 62% | 30% |
| Qwen3-30B (11/03~12) | 159 | 85% | 53% | 33% | 20% |
| NVIDIA laguna (11/14) | 47 | 87% | 74% | 28% | 2% |

- 주의: 테스트 사용이라 일부러 날카로운 문장을 많이 쳤고, 입력 중 요청(미완성 문장)도 섞여 있다. 81~87%가 전부 틀린 알림이라는 뜻은 아니다.
- **무난한 문장도 문턱에 걸린다(Qwen + 판별기)**: Qwen의 s는 0.3이 가장 많고(159건 중 60건), 판별기 값은 대부분 0.3~0.4다. s 0.3 + clf 0.35 + 겉 신호 없음이면 위험도 0.31로 문턱 0.3을 **바로 위에서** 넘는다. 판별기가 0.33이냐 0.36이냐로 무난한 문장의 알림이 갈린다.
- **s는 연속 값이 아니다(E-03 보강)**: Qwen은 0.3·0.8·0.6·0.7, laguna는 0.85·0.7·0.1 정도만 낸다. 사실상 2~3단계 라벨이라 문턱을 조금 움직이면 한 덩어리가 통째로 넘어온다.
- 지금(laguna, 판별기 없음, 문턱 0.3)은 "모델이 s 0.7 이상을 주면 알림"과 같다. 겉 신호는 결과에 거의 영향이 없다.

**흔들림: 11/14에 다섯 번 중 한 번은 모델 답이 없다**
- 11/14 60건: alert 41 · none 6 · **abstain 13(22%)**. `/health`의 nvidia TimeoutError 13과 같은 수.
- 학교 GPU 때(11/03~12)는 기권 0~11%.
- "시발련아"는 모델이 오면 위험도 약 0.65(prior 0.5, s 0.85)로 문턱과 멀다. 떴다 안 떴다의 원인은 문턱이 아니라 **시간 초과**다.

- 문턱을 기본값(0.6 / 0.4)으로 되돌리면 알림은 답한 건의 약 30%로 준다. laguna에서는 "겉 신호 + 모델이 함께 가리킬 때만 알림"이 된다(s 0.85 단독은 0.46).

- 0.6이 맞는 값인지는 사람 라벨 45개로 재야 한다(지금은 "덜 틀리는 쪽"일 뿐).

## 13. 사람 라벨로 실제 모델 평가 (11/14, 라벨을 모델에 처음 사용)

방법: T-16 60문장을 지금 운영과 같은 실시간 설정(NVIDIA laguna-xs-2.1, 판별기 없음, `tone_label` 프롬프트)으로 5회, 총 300회. 판단과 속도를 따로 보려고 전문가 마감만 8초로 늘렸다. 회차마다 캐시를 비웠다. 원자료·스크립트: `eval/results/t16_laguna_5runs_2026-11-14.json`, 도구는 `eval/live_eval.py`(P-40, `run`·`report`. 이 PC의 `.env`에 `NVIDIA_API_KEY` 필요).

**문턱별 결과 — 확실한 구간 45문장(5:0 + 4:1), 5회 합산 225건**

| 알림 문턱 | 정밀도 | 재현율 | 알림 비율 | 틀린 알림 | 놓침 |
|---|---|---|---|---|---|
| 0.3 (지금 운영) | 0.73 | 0.91 | 78% | 47 | 12 |
| **0.45** | **0.88** | **0.79** | 56% | 15 | 29 |
| 0.5 | 0.92 | 0.62 | 42% | 8 | 53 |
| 0.6 (기본값) | 1.00 | 0.18 | 11% | 0 | 115 |
| 0.7 | 알림 없음 | | | | |

- 만장일치 29문장만 봐도 같은 모양(0.3: 0.71/0.94, 0.45: 0.87/0.80, 0.5: 0.95/0.64, 0.6: 1.00/0.18).
- 3:2로 갈린 15문장: 0.3에서 65%, 0.45에서 45%, 0.5에서 28%에 알림. 여기는 정답이 없는 구간이라 알림이 적을수록 좋다.
- **12절의 "0.6으로 되돌리기" 권고를 고친다.** 판별기가 없는 지금 0.6이면 "신경 꺼", "알아서 하세요", "별로", "바빠"처럼 5명이 모두 고른 문장도 전부 놓친다(겉 신호가 0.35 이상 붙은 문장만 알림). **0.45를 권한다**: s 0.85면 단독으로, s 0.7이면 겉 신호가 조금 있을 때(prior 0.2 이상) 알림. 0.5는 정밀도가 0.04 높지만 "알아서 해"·"알아서 하세요"(겉 신호 없음)를 놓친다.

**틀리는 방향 (문턱 0.3 기준, 확실 45)**
- 틀린 알림 9문장은 거의 다 **무난한 말 + 무거운 맥락**: 면접 떨어진 친구에게 "괜찮아", 휴학 얘기하자는 아빠에게 "알았어", 실수를 사과하는 팀원에게 "확인했습니다", 장학금 받았다는 친구에게 "축하해". 사람은 0~1명만 골랐다. Codex 라벨러와 같은 방향(LLM은 맥락·기대로 판단). 즉 **모델의 "틀린 알림"이 바로 답장 도우미(B) 영역**이다.
- 놓침 2문장: "내가 알아서 할게"(5:0, s 0.2), "ㅎㅎ"(4:1).

**자기 일치도 (같은 문장 5회)**

| 문턱 | Fleiss kappa | 5회 중 결과가 갈린 문장 |
|---|---|---|
| 0.3 | 0.86 | 7/60 |
| 0.45 | 0.89 | 7/60 |
| 0.6 | 1.00 | 0/60 |

- 사람 5명끼리는 0.47. **모델은 자기 자신과는 사람끼리보다 훨씬 잘 일치한다.** s 값이 5회 모두 같은 문장 43/60, 읽힘 이름이 바뀐 문장 8/60.
- s는 세 값뿐이다: 0.85(118회) · 0.7(99회) · 0.1(65회). 사실상 3단계 라벨(E-03 확인).
- 그래서 "같은 말에 떴다 안 떴다"의 주원인은 판단의 흔들림(60문장 중 7문장)이 아니라 **속도**다: 모델 지연 p50 0.54초 · p90 1.86초 · p95 2.92초 · 최대 7.9초, **1.35초 초과 12%**(DB·네트워크 제외). 운영 trace의 기권 22%와 맞는다.

**한계**
- 45문장, 5회는 독립이 아니다(같은 문장 반복). 정밀도 0.88은 ±0.1쯤으로 읽어야 한다.
- 이 세트는 60%가 "알려 줄 만함"인 어려운 문장 모음이다. 실제 대화는 대부분 무난한 말이라 **실제 정밀도는 이보다 낮다**. 참고: 사람이 괜찮다고 한 문장에 알림이 뜬 비율은 0.3에서 55%, 0.45에서 18%, 0.5에서 9%, 0.6에서 0%.
- 라벨러 5명 중 2명이 팀원. 판별기를 켠 학교 GPU 설정(Qwen)은 재지 못했다.

**정리**
- 형에게 부탁할 것: `.env.pilot.engine`의 `HINT_ALERT_THRESHOLD`를 0.3 → **0.45**. `HINT_MIN_CONFIDENCE`는 이 모델의 확신이 0.78~0.92라 어느 값이든 영향 없다.
- 흔들림은 문턱으로 못 고친다. 다음 손댈 곳은 속도(E-23·24·25)와 "모델이 못 와도 분명한 구간은 결정"(E-01).

## 14. 혼자 진행한 것 (11/14 오후, 브랜치 `feature/t16-live-eval`)

사용자 지시: "커밋하고, 혼자 할 수 있는 것 최대한 진행하고 깃허브에 올려". main에는 합치지 않고 브랜치로 올렸다(형이 운영 중인 엔진이 main을 쓰므로 합치기는 확인 뒤에).

| 작업 | 내용 | 확인 |

| P-40 | `eval/live_eval.py`: 사람 라벨 세트로 실제 실시간 모델을 여러 번 돌리고(`run`) 문턱별 정밀도·재현율·자기 일치도·지연을 낸다(`report`) | 테스트 7개, 11/14 실측에서 13절 표가 다시 나옴 |

**손대지 않은 것과 이유**
- 모델이 못 왔을 때 겉 신호만으로 알리기(E-01): 규칙 3("모두 실패하면 기권")과 부딪친다. 규칙을 바꿀지는 사용자 결정.
- 입력 중 호출 줄이기(E-24): 앱 동작이 바뀐다. 사용자 결정.
- 실시간 프롬프트에 최근 대화 넣기(E-10): 지금 세트(직전 한 줄뿐)로는 좋아졌는지 잴 수 없다. T-16b 라벨 뒤에.
- 차단기(E-25): `/health`에 `breaker_open` 기록이 없다. 11/14에는 실제로 열리지 않았다. **관찰되지 않은 문제라 고치지 않았다.**

**실험 1 — 같은 요청을 두 번 보내면 빨라지나(T-33 근거)**: T-16 60문장, 같은 모델에 동시에 2번.

| 방식 | 1.35초 초과 | p90 | p95 | 추가 호출 |
|---|---|---|---|---|
| 한 번만 | 12% | 2.9초 | 7.3초 | – |
| 동시에 두 번 | 8% | 1.3초 | 3.9초 | 100% |
| 0.6초 뒤에 한 번 더 | 10% | 1.5초 | – | 53% |

- 꼬리는 줄지만(p90 절반) **마감 초과는 12% → 8%에 그친다.** 느릴 때는 두 요청이 같이 느리다. 분당 40회 한도를 두 배로 쓰는 값에 비해 얻는 게 작다. 60문장 한 번이라 5건과 7건의 차이다(오차 큼).
- 다른 모델과 짝지은 경우는 재지 않았다.

**실험 2 — temperature 0이면 덜 흔들리나**: 같은 60문장 5회.

| | temperature 0.2 | temperature 0 |
|---|---|---|
| 자기 일치도(문턱 0.45) | 0.89 | 0.91 |
| 5회 중 결과가 갈린 문장 | 7/60 | 5/60 |
| 정밀도·재현율(확실 45, 0.45) | 0.88 · 0.79 | 0.88 · 0.79 |

- 차이가 거의 없다. 0으로 해도 완전히 같아지지 않는다(공급자 쪽 비결정성). **E-08은 우선순위를 내린다.**
- 이 회차의 마감 초과는 7%였다(13절은 12%). 시간대에 따라 달라진다.

**정리: 흔들림은 설정 몇 개로 못 고친다.** temperature도, 같은 모델 중복 요청도 답이 아니다. 남는 선택지는 ① 더 빠르고 고른 모델(학교 GPU 복구, Qwen 평균 0.66초) ② 전송 확인 때만 판정하고 그때는 조금 더 기다리기 ③ 분명한 구간을 규칙으로(규칙 3 변경 필요). 모두 사용자 결정이 필요하다.

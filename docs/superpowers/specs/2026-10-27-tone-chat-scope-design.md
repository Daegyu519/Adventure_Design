## 1. 의도

보내려는 문장이 상대에게 어떻게 읽힐지 보내기 전에 조용히 알려 준다. 판정은 내 의도를 모르는 쪽(받는 사람 눈)이 하고, 고칠 때는 오해를 부르는 신호만 최소로 바꾸고, 고르는 건 내가 한다(기획서).

이번 추가의 이유:
- 파일럿 참가자가 1주 동안 카톡 대신 이 앱으로 대화해야 힌트·하소연 데이터가 쌓인다. 답장·공감·읽음·사진 같은 기본기가 모자라면 참가자가 카톡으로 돌아간다. *(제 추정)*
- 기획서의 고리("거울 → 실전 알림 → If case → 습관")에서 거울 세션이 빠져 있었다. 사용자가 모두 넣기로 했다.
- 하소연 익명성은 3명 이상 방에서만 지킬 수 있다(기획서 "익명성 지키기" 3번). 그래서 그룹방이 필요하다.

## 2. 목표 · 비목표 · 반목표

**목표**
- 파일럿(10~15쌍 + 팀 그룹방)이 1주 동안 메신저로 쓸 수 있는 채팅 기본기 (3장 표의 '채택')
- 실시간 힌트, 살펴보기(의도 칩 + 바뀐 곳 강조), 털어놓기, 거울 세션 3종, 리포트
- 카톡과 구분되는 차분한 디자인 시스템 (라이트 · 다크)
- 두 Claude 계정이 같은 맥에서 충돌 없이 나눠 작업

**비목표** (이번에 하지 않음)
- 선물·쇼핑·지갑·이모티콘 상점, 오픈채팅, 보이스톡·페이스톡·보이스룸, 톡게시판(투표·일정), 예약 메시지, 할 일, 클라우드 백업, 멀티프로필, 미니게임
- 번역·맞춤법·대화 요약 같은 범용 AI 기능
- 출시, 스토어 심사

**반목표** (돌아가도 이러면 실패)
- 힌트가 전송을 막거나 늦춘다
- 힌트·리포트·거울이 사람을 평가한다 ("당신은 차가운 사람")
- 털어놓은 사람이 누구인지 짐작된다 (1:1 방에서 방 패턴이 쌓이는 경우 포함)
- 문장을 통째로 다시 쓴다. 카톡 'AI 말투 변경'과 같아지고 차별점이 사라진다
- 카톡처럼 보인다 (노란색·갈색, 꼬리 달린 말풍선 복제)
- 거울 세션이 게임처럼 시끄럽다 (점수 폭죽, 연속 출석 압박)

### 카톡 AI 말투 변경에서 확인한 것
UI 문구 근거: "상황에 맞는 말투, AI로 재치있게 변경해 드려요"(`Setting_Laboratory_AI_Setting_Tone_Description`), "입력창에 적용하기", 결과 피드백 "좋아요 / 어색해요", AI 데이터 처리 동의 창, 입력 내용·결과 3개월 보관 고지.

우리 쪽에 반영하는 것:
1. **차별점의 근거**: 카톡은 스타일을 통째로 바꾼다. 우리는 판정(받는 사람 눈) → 최소 수정 → 사용자 선택이다. 발표에서 비교 슬라이드로 쓴다.
2. **"입력창에 적용하기"** 흐름은 살펴보기 시트에서 그대로 쓴다 (T-22의 "고른 문장이 입력창에 들어감").
3. **AI 데이터 처리 동의 창**처럼 첫 실행 동의 화면을 둔다. 파일럿 동의서(T-31)와 개인정보 규칙(하소연 원문 미저장 등)을 여기 보여 준다.

## 4. 그룹방 도입에 따른 변경 (ARCHITECTURE 5장 · 3장 · 4장)

### 데이터

| 표 | 바뀐 칸 |
|---|---|
| `public.rooms` | id, kind(`direct`·`group`), title(그룹만), relation, created_by, created_at. **user_a, user_b 삭제** |
| `public.room_members` (새) | room_id, user_id, joined_at, last_read_at, muted. PK(room_id, user_id) |
| `public.messages` | + reply_to(bigint, 같은 방), + image_path, + mentions(uuid[]). 수정·삭제 없음 유지 |
| `public.reactions` (새) | message_id, user_id, emoji(고정 6개 중), created_at. PK(message_id, user_id) |
| `public.invites` | + room_id(그룹 초대면 채움), + max_uses. `accept_invite(code)`가 1:1 방 생성 또는 그룹 참여 |
| `public.mirror_attempts` (새, 5장) | 본인 행만 |
| `tone.pair_patterns` → `tone.sender_patterns` | sender_id, relation, trigger, count, strength, feeling, active_from, updated_at. PK(sender_id, relation, trigger). 아래 반영 규칙 적용 |
| Storage `chat-images` | 경로 `room_id/…`. 방 멤버만 읽기·쓰기 |

- RLS는 `is_member(room_id)` security definer 함수 하나로 통일한다.
- 입력 중 표시는 Realtime Presence(방 채널)로만 하고 DB에 남기지 않는다.
- 그룹 인원 상한 8명 *(제 판단: 파일럿 팀플 규모)*.

### 하소연(털어놓기) 반영 규칙 — 기획서 "하소연 방식" 절을 따름
기획서: "누가 말했는지는 빼고 **민수의 말투 패턴에만** 반영", "한 사람이 아닌 **관계 전체에** 적용 — 팀원 누구에게 보낼 때든 똑같이", "**3명 이상인 팀에서만** 켠다", "반영 시점을 며칠 늦춘다".
- 패턴의 주인은 **털어놓기 대상 메시지를 보낸 사람**이다. 키는 (보낸 사람, 관계, 신호)다. 그 사람이 같은 관계의 어느 방에서 쓰든 적용한다. 털어놓은 사람의 문장에는 적용하지 않는다.
- **그룹방(3명 이상)에서 나온 하소연만** `tone.sender_patterns`에 넣는다. `active_from` = 다음 날 0시. 관계별 주간 상한(T-24)은 그대로 둔다.
- **1:1 방에서 나온 하소연**은 `tone.global_patterns`(신호별 전체 수)에만 더한다.
- 반영 방식은 ARCHITECTURE 그대로다. L0 사전점수와 L3 `pattern` 항으로만 들어가고, `global_patterns[trigger] ≥ global_min_obs`일 때만 반영한다. 원래 패널이 낼 법한 경고만 강해지고, 없던 경고를 새로 만들지 않는다.
- 털어놓기 버튼은 두 방 모두에 있다.

### 엔진
- `/v1/hint`, `/v1/detail`: 방 참여 확인은 `room_members`로 한다. 최근 대화 8개에 화자 표시(나 / 상대1 / 상대2…)를 붙인다. 입력 중인 문장이 답장이면 원문 메시지를 맥락 맨 앞에 넣는다.
- 그룹방 판정 기준은 "이 방 사람들이 읽을 때"다. 관계는 방 단위 하나다.
- 웹훅 → 푸시는 방 멤버 전원(보낸 사람·알림 끈 사람 제외)에게 보낸다.

## 5. 거울 세션 · 의도 칩 · 바뀐 곳 강조 (새 기능, 기획서 기준)

### 거울 세션 (하루 2분, 카드 3장)
1. **역할극**: AI 인물(예: 팀원 민지)이 상황 메시지를 먼저 보낸다 → 내가 평소처럼 답한다 → "받았을 때 속마음" 한 줄, 읽힘(자주/가끔/드물어요 세 단계, `/v1/detail`과 같은 표현), If case(그대로 / A / 직접 고치기).
2. **되돌려 받기**: 내가 예전에 보낸 문장을 AI 인물이 보낸 것처럼 보여 준다 → "받으면 얼마나 차갑게 느껴지나요" 1~5점 → 공개 "이건 지난주 목요일에 당신이 팀원에게 보낸 문장이에요". 보낸 문장이 아직 없으면 상황 카드 문장으로 대신한다.
3. **예측 맞히기**: 내 문장과 관계("선배라면?")를 보여 주고, "선배가 얼마나 부정적으로 읽을까" 1~5점을 먼저 고르게 한다. 패널의 부정 확률(차갑게+성의없게+화나게)을 같은 1~5칸으로 나눠(0.2 간격) 비교한다. `gap = |예측 칸 − 패널 칸|`이 자기객관화 점수다. 되돌려 받기 점수도 같은 방식으로 gap을 낸다 *(제 판단)*.

- 문장 출처: 본인이 보낸 메시지(엔진이 서비스 키로 읽음)와 `engine/content/mirror_cards.yaml`(팀플 상황 카드: 일정 조율, 역할 요청, 거절, 마감 독촉. 20장부터 시작).
- 실제 대화에서 뽑은 카드는 Gemini 무료 등급에 보내지 않는다 (CLAUDE.md 규칙 9).
- 피드백은 문장에만 한다. 점수 표현은 "예측과 한 칸 차이"처럼 차이로만 보여 준다.

새 API:

| 메서드 | 경로 | 요청 | 응답 |
|---|---|---|---|
| POST | `/v1/mirror/today` | 없음 | `{cards: [{card_id, kind: "roleplay"\|"receive"\|"predict", persona, relation, situation, message}]}` |
| POST | `/v1/mirror/answer` | `{card_id, reply?, score?, predicted?}` | `{readings, inner_voice?, reveal?, options?, gap?}` |
| GET | `/v1/stats/me` (확장) | 없음 | 기존 + `{predict_gap_trend, hints_by_week}` |

`card_id`는 엔진이 서명한 값이라 앱이 문장 출처를 위조할 수 없다 *(제 판단)*.

### 의도 칩과 바뀐 곳 강조 (살펴보기 시트)
- 시트 맨 위에 "단호하게 / 미안하게 / 가볍게" 칩. 고르지 않아도 된다.
- 판정 단계에는 의도를 넣지 않고 고쳐 쓰기 단계에만 넣는다 (기획서 SimToM 근거).
- 어긋남 표시는 가장 많이 읽힌 뜻이 아래에 해당할 때만 한 줄 띄운다. 단호한 거절이 "차갑게" 읽히는 것은 어긋남으로 보지 않는다(단호함을 지키는 것도 사용자의 선택) *(제 판단)*.

| 의도 칩 | 어긋남으로 보는 읽힘 |
|---|---|
| 단호하게 | 화나게, 성의없게 |
| 미안하게 | 차갑게, 화나게, 성의없게 |
| 가볍게 | 차갑게, 화나게 |

- 시트가 열린 뒤 칩을 누르면 `/v1/detail`을 `intent`만 바꿔 다시 부른다. 판정 전문가 입력에는 의도가 없으므로 라우터 캐시(같은 전문가, 같은 입력)에 걸려 고쳐 쓰기만 새로 돈다. 별도 API는 만들지 않는다.
- 후보 문장은 원문과 달라진 어절만 강조한다. 비교는 앱에서 어절(띄어쓰기) 단위로 한다 *(제 판단)*.

## 7. 디자인 방향

ui-ux-pro-max 데이터베이스의 "Chat & Messaging App" 항목(미니멀 + 작은 상호작용, 브랜드 색 + 보낸/받은 말풍선 대비 + 입력 중 회색)을 기본으로 했다. 도구 기본 추천 중 랜딩 페이지 패턴, Exaggerated Minimalism, Lora/Raleway 글꼴(한글 없음)은 버렸다.

- **색**: 차분한 틸(주색), 중립 회색, 힌트용 앰버, 거울용 라벤더. 빨강은 오류에만 쓴다. 시작 값 (라이트 / 다크):

| bubble-other | #F1F5F4 | #1E2B2A |

- **글꼴**: Pretendard(OFL, `expo-font`로 포함). 본문 16, 줄 간격 1.5.

- **움직임**: 150~250ms. 힌트는 입력창 위에서 8px 올라오며 나타난다. 시스템 '동작 줄이기'를 따른다. 힌트에 진동을 쓰지 않는다.

- **말풍선**: 꼬리 없음, 둥근 모서리 18. 노란색·갈색 계열 금지.
- **산출물 순서**: `design-system/tone-chat/MASTER.md` → HTML 목업(대화방+힌트, 살펴보기, 털어놓기, 거울 3카드, 리포트, 대화 목록)을 먼저 보여 드리고 승인 → 앱 테마 토큰 파일 → 화면 구현.
- 접근성: 대비 4.5:1 이상, 터치 영역 44pt 이상, 스크린리더 라벨.

## 9. 두 계정 협업 (같은 맥, 로컬만)

**두 번째 계정 실행**: 한 설정 폴더에서는 로그인이 하나만 유지된다. 두 번째 계정은 설정 폴더를 따로 쓴다 (Claude Code 공식 방식).
```bash
alias claude-b='CLAUDE_CONFIG_DIR=~/.claude-b claude'
```
주의: `~/.claude-b`는 비어 있어서 스킬·플러그인·MCP(REA 포함)가 없다. 프로젝트 규칙과 진행 상황은 저장소 안(`CLAUDE.md`, `docs/`)에 두어 두 계정이 같은 내용을 보게 한다. 필요한 플러그인은 B 계정에서 따로 설치한다.

**작업 흐름**
- 저장소 하나(`~/Projects/tone-chat`, 브랜치 `main`). 작업마다 worktree를 만든다: `~/Projects/tone-chat-wt/<브랜치>`. 브랜치 이름은 CLAUDE.md 규칙(`t07-login`)대로.
- **작업 잡기**: `mkdir ~/Projects/tone-chat/.coord/claims/T-07`이 성공한 쪽이 가져간다. 동시에 잡아도 하나만 성공한다. 안에 `owner`(a/b), 브랜치, 시작 시각을 적는다.
- **기록**: `.coord/log.md`에 한 줄씩 덧붙인다(시각, 계정, 작업, 상태, 다음 사람에게 남길 말). 세션이 끊겨도 이 기록으로 이어받는다.
- **합치기**: 테스트 통과 → `mkdir .coord/merge.lock` → main에 합침 → `docs/tasks.md` 상태를 `완료`로 + 확인 방법 한 줄 → 잠금 해제. 한 번에 한 계정만 합친다.
- `.coord/`는 git에 넣지 않는다(같은 맥이라 파일로 공유).
- **기본 분담**: A(이 계정) = 앱·디자인, B = 엔진·DB·평가. 자기 영역이 비면 다른 영역 작업도 잡는다. 선행 작업은 tasks.md의 '선행' 칸을 따른다.
- 이 규칙은 `docs/COLLAB.md` 한 장과 작은 스크립트 2개(`scripts/claim`, `scripts/land`)로 둔다.
- **PR 규칙 대신 `land`**: 원격 저장소가 없으므로 CLAUDE.md의 "한 작업 = 한 PR"은 "한 작업 = 한 브랜치 = 한 번의 `land`"로 바꾼다. `land`는 엔진 테스트·앱 타입 검사를 돌리고, 프롬프트·`models.yaml`·가중치가 바뀐 브랜치면 `eval/run_eval.py`(mock)를 돌려 `eval/baseline.json`보다 정밀도가 떨어지면 합치지 않는다. 결과는 merge 커밋 메시지에 붙인다 *(제 판단)*.
- 사람 팀원이 다른 컴퓨터에서 코드를 같이 쓰게 되면 그때 GitHub 비공개 저장소로 옮기고, `.coord` 잡기 대신 PR을 쓴다. 지금은 사용자 결정대로 로컬만 쓴다.

**하네스 모델** (서브에이전트만, Sonnet·Opus로 제한): 설계·코드 리뷰·엔진 집계/라우터 같은 까다로운 로직은 Opus, 화면 구현·테스트 작성·조사는 Sonnet. 앱 엔진이 쓰는 모델(NVIDIA·Gemini 등)은 이 제한과 무관하다.

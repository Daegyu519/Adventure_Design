## 0. 피드백과 방향 구분

교수님 피드백:
- 디자인이 AI가 만든 화면처럼 보임. 메신저 레퍼런스 하나를 확실히 정할 것.
- 사용자를 새 채팅 앱으로 초대해야 하는 장벽을 줄이고, 기존 메신저 옆에서 도움받는 방안을 검토할 것.
- 사람의 감정을 다섯 가지로 판단하는 접근과 표현을 재검토할 것.
- 간헐적인 속도 병목을 해결할 것.
- 기존 제품과 차이점을 시장조사로 설명할 것.
- 거울 기능은 긍정적이나 이름이 기능을 이해시키지 못함.
- 기술 추가뿐 아니라 접근성과 사용자 친화성을 개선할 것.

사용자가 제시한 방향:
- 복사·붙여넣기를 핵심 사용 방식으로 삼으면 일반 LLM 대비 이점이 약함.
- 설치형 키보드 또는 특정 메신저 하나와의 연결을 검토.
- 기존 앱·엔진을 최대한 재사용하고, 연결부를 교체할 수 있는 어댑터 구조를 검토.
- 실제 수요, 판정 근거의 타당성, 개선 방법을 함께 검증할 것.

아직 확정하지 않은 것:
- 첫 타깃 사용자·상황, 첫 외부 플랫폼, 키보드 채택 여부, 최종 기능 이름.
- 아래의 팀플 타깃·Android 우선·대화 연습 명칭은 검증할 제안이다.
- 대형 기업의 미래 API 제공을 전제로 개발하지 않는다. 현재 가능한 기능으로 검증한다.

## 1. R-01 — 누가 왜 쓰는지와 시장 이해

초기 가설: 대학생 팀플의 부탁·재촉·거절에서 의도는 유지하면서 불필요한 오해를 줄인다. “차가운 말투를 알고 싶다”라는 욕구가 실제로 있는지부터 검증한다.

- [ ] 초기 타깃과 핵심 상황을 하나 정한다.
- [ ] 6~8명 정도를 대상으로 최근 실제 경험을 인터뷰한다. 이 규모는 탐색용이며 시장 규모의 증거로 쓰지 않는다.
- [ ] 질문: 최근 오래 고친 메시지, 걱정한 결과, 해결 방법, 친구/LLM에게 확인한 경험, 도움받고 싶은 순간과 간섭받기 싫은 순간.
- [ ] “있으면 쓰겠는가”보다 반복 빈도·실제 소요 시간·현재 대처 행동을 기록한다.
- [ ] 대화 원문 수집은 필수로 하지 않는다. 상황 설명·재구성 예문으로 시작한다.
- [ ] Grammarly, 삼성 글쓰기 어시스트, 일반 LLM을 실제 동일 시나리오로 비교한다.
- [ ] 비교표: 한국어 맥락, 원래 의도·단호함 유지, 설명의 구체성, 사용 단계 수, 필요한 권한, 관점 전환 연습.
- [ ] 제품 설명 한 문장과 “사용하지 않아도 되는 상황”을 작성한다.
- [ ] 수요가 약하면 타깃·상황을 수정하거나 해당 방향을 보류한다.

완료 기준: 인터뷰 요약, 동일 시나리오 경쟁 비교표, 타깃·핵심 문제·차별화 가설 및 계속/수정/보류 결정이 남는다. 차별화는 검증 전까지 가설로 표시한다.

## 2. R-02 — 판정과 근거를 어떻게 평가할지 정의

사람의 실제 감정을 단정하기보다, 문장이 특정 맥락에서 어떻게 읽힐 수 있는지 다룬다. 감정 범주를 단순히 늘리는 것으로 해결하지 않는다.

- [ ] 현재 차가움/부정성 판정이 후속 해석을 제한하는 지점과 다섯 범주의 역할을 코드에서 확인한다.
- [ ] 복수 해석·판단 어려움·맥락 부족을 표현하는 기준을 정한다.
- [ ] 평가를 세 축으로 구분한다: 해석의 타당성 / 지적한 구절·맥락의 타당성 / 수정안의 유용성.
- [ ] T-16·P-16 도구를 재사용해 사람이 독립적으로 라벨하고, 최소 30쌍 대조 세트 및 일치율·불일치 사례를 기록한다.
- [ ] 라벨 항목에 경고 필요 여부, 문제 구절, 해석 이유, 판단을 바꾸는 맥락, 의도 유지 여부를 포함한다.
- [ ] 정당한 거절·재촉·기한·단호함을 약하게 만드는 수정안을 실패 사례로 포함한다.
- [ ] 친한 사이의 짧은 답, 농담, 존댓말/반말, 맥락에 따라 뜻이 바뀌는 사례를 포함한다.
- [ ] 설명이 입력에 없는 사실이나 상대의 속마음을 지어내지 않는지 검사한다.
- [ ] 설명이 그럴듯한지만 보지 않고, 관련 구절·맥락을 제거/교환했을 때 판정도 적절히 바뀌는지 진단한다.
- [ ] 모델의 설명문을 내부 추론이 정확히 재현된 증거로 취급하지 않는다.
- [ ] 학습/가중치 조정용 자료와 최종 평가 자료를 분리한다.
- [ ] 최신 Qwen 단독·분류기 단독·결합을 같은 조건에서 비교한다. mock 숫자를 실제 품질로 보고하지 않는다.
- [ ] 채택 기준과 경고 빈도·오탐·놓침의 허용 범위를 결과를 보고 조정하기 전에 문서화한다.

완료 기준: 라벨 지침, 사람 평가 결과, 비교표, 실패 유형, 채택 기준이 재현 가능한 형태로 남는다.

## 3. R-03 — 외부 연결 하나의 가능성 실험

목표: 상대방을 새 앱에 초대하지 않아도, 사용자가 보내기 전에 개인적인 도움을 받을 수 있는지 확인한다.

- [ ] 후보별로 초안 접근 / 이전 대화 / 답장 대상 / 개인 안내 / 수정 적용 / 전송 전 개입 가능 여부를 표로 만든다.
- [ ] Android 설치형 키보드: 한 메신저 입력창에서 초안 읽기·분석·안내·수정 적용을 작은 프로토타입으로 검증한다.
- [ ] 한글 조합·커서·선택·줄바꿈·삭제·키보드 전환의 구현 부담과 사용할 기기를 확인한다.
- [ ] 키보드가 입력한 문장을 아는 것과 대화 전체를 아는 것을 구분하고, 맥락 확보 가능 범위를 기록한다.
- [ ] 대안으로 Telegram 사용자 클라이언트 API의 로그인·대화 조회·전송 전 분석 가능 범위를 조사한다.
- [ ] Discord·Telegram의 일반 봇이 전송된 메시지를 받는 것과 작성 중 초안을 분석하는 것을 구분한다.
- [ ] Kakao 공개 API가 일반 대화방의 초안을 제공한다고 가정하지 않는다.
- [ ] 권한·공식 지원 범위·플랫폼 정책·개발 비용·사용자 부담을 확인한다.
- [ ] Expo 앱 재사용 범위와 별도로 필요한 네이티브 입력기/클라이언트 작업을 구분한다.
- [ ] 첫 구현 대상 하나를 선택하고, 선택 이유와 지원하지 못하는 기능을 기록한다.

완료 기준: 실제 가능한 작은 실험 결과와 플랫폼 선택 근거가 남는다. 봇의 사후 분석을 전송 전 분석으로 시연하지 않는다. 범용 키보드와 여러 메신저를 동시에 완성하려 하지 않는다.

참고: 현재 추천 후보는 Android 키보드 실험이지만, 채택 확정은 아니다.

## 4. R-04 — 공통 분석과 어댑터 경계 구현

R-01~03의 결과로 범위를 확정한 뒤 설계한다. 현재 앱의 신뢰 경계와 다른 외부 맥락 입력은 기존 API에 무조건 허용하지 않는다.

- [ ] 기존 인증·방 멤버 확인·Supabase 맥락 조회와 공통 분석 파이프라인의 결합 지점을 정리한다.
- [ ] 공통 입력을 정의한다: 초안, 허용된 맥락, 화자/관계, 답장 대상, 맥락 유무, 요청 취소·기한.
- [ ] 외부 연결의 인증·권한·데이터 출처·멤버십 확인 방식과 현재 앱의 방식 차이를 설계한다.
- [ ] 어댑터 기능 표에 따라 지원하지 않는 정보를 명시하고, 없는 맥락을 추정해서 채우지 않는다.
- [ ] 공통 출력은 주의 구절·가능한 해석·대안·판단 어려움 등을 검토한다. API 변경 시 생성 타입을 갱신한다.
- [ ] 개인정보 가리기와 원문 저장 제한을 모든 입력 경로에 적용한다.
- [ ] 첫 어댑터 하나와 기존 앱을 같은 분석 코어에 연결한다.
- [ ] 기존 앱은 채팅·대화 연습·평가 공간으로 재사용할 범위를 정한다.
- [ ] 기존 아키텍처와 다른 설계는 구현 전에 범위를 합의하고 ARCHITECTURE.md에 반영한다.

완료 기준: 첫 외부 경로에서 분석·개인 안내·수정 적용이 동작하며 기존 앱 경로도 유지된다. 지원 범위와 보안 경계가 문서화된다.

## 5. R-05 — 병목 측정과 속도 개선

기준 측정은 R-03과 함께 시작할 수 있다. 병목을 확인하기 전에 모델부터 교체하지 않는다.

- [ ] 인증, 맥락 조회, 모델 대기, 추론, 집계, 통신, 화면 표시를 구간별로 측정한다.
- [ ] 단일 요청과 동시 요청, 첫 요청과 반복 요청, 느린 네트워크에서 p50·p95·시간 초과율을 비교한다.
- [ ] 엔진 처리 시간과 사용자가 누른 순간부터 결과가 보일 때까지의 시간을 구분한다.
- [ ] 현재 P-34의 최대 1.5초 동작을 배포 버전과 실제 기기에서 확인한다.
- [ ] 모델은 응답했지만 클라이언트 기한 때문에 안내되지 못한 경우를 구분한다.
- [ ] 원인에 맞게 대기열·호출 수·맥락 조회·토큰 수·모델 배치를 개선하고 전후 품질도 비교한다.
- [ ] 취소·늦은 응답·연타·앱 이탈·엔진 장애에서 중복 전송/초안 유실이 없는지 확인한다.
- [ ] 외부 플랫폼에서 전송 제어가 가능한 범위를 명시하고, 보장하지 못하는 동작을 약속하지 않는다.

완료 기준: 병목 구간, 전후 측정표, 남은 제한이 기록된다. 속도를 위해 품질과 개인정보 경계를 조용히 낮추지 않는다.

## 6. R-06 — 메신저 UX와 기능 이름 정리

- [ ] 모바일 대화 흐름의 주 레퍼런스 하나를 선정한다. 현재 제안은 카카오톡이며 최종 선택은 별도 기록한다.
- [ ] 대화 목록·말풍선·시간·읽음·답장·입력창·메뉴의 배치 원칙을 정한다. 타사 브랜드·로고·에셋은 쓰지 않는다.
- [ ] 대화방·분석 안내·대화 연습 화면부터 시안을 만든다.
- [ ] 대화가 화면의 중심이 되도록 설명·카드·AI 버튼의 비중을 조정한다.
- [ ] 다섯 감정 점수 나열보다 주의 구절 → 가능한 해석 → 선택 가능한 대안 중심 표현을 시험한다.
- [ ] “거울모드” 대체 이름을 사용자에게 확인한다. 후보: 대화 연습.
- [ ] 세부 기능 이름 후보를 검증한다: 상대 입장에서 읽기 / 답장 연습 / 어떻게 들릴까?
- [ ] AI 안내를 닫거나 무시하고 원래 의도로 보낼 선택을 분명히 한다.
- [ ] 첫 사용자에게 설명 없이 주요 과업을 수행하게 하고 막히는 지점을 기록한다.
- [ ] 작은 화면·키보드·다크 모드·글자 확대·스크린리더를 실제 기기에서 확인한다.

완료 기준: 일관된 레퍼런스와 수정 전후 화면, 과업 수행 관찰 결과가 남는다. 이름과 디자인의 최종안은 별도 확정한다.

## 7. R-07 — 파일럿·피드백·개선 주기

- [ ] P-15 지표 집계를 구현하고 T-31 파일럿과 연결한다.
- [ ] 경고 빈도, 표시까지의 지연, 시간 초과/실패, 수정/원문 전송, 끄기·반복 사용을 개인정보 최소화 방식으로 집계한다.
- [ ] 판정 동의 / 설명 타당성 / 수정안 유용성 / 실제 대화 도움을 구분해 피드백 받는다.
- [ ] “불필요한 경고”, “맥락이 다름”, “의도가 바뀜”, “너무 느림” 등 실패 유형을 기록한다.
- [ ] 수정률만으로 관계 개선이나 오해 감소를 주장하지 않는다. 짧은 설문·인터뷰를 함께 시행한다.
- [ ] 틀린 사례 분류 → 원인 가설 → 한 가지 수정 → 보관 평가 세트 재검증 → 파일럿 비교 순서로 개선한다.
- [ ] 사용자 동의와 검토 없이 대화 원문·하소연·피드백을 자동 학습 자료로 전환하지 않는다.
- [ ] 즉시 안내와 대화 연습이 각각 언제 쓰이고 며칠 뒤에도 다시 사용되는지 확인한다.
- [ ] 결과에 따라 타깃·플랫폼·경고 방식의 유지/수정/보류를 결정한다.

완료 기준: 사용 지표와 정성 피드백, 개선 전후 비교, 다음 결정이 남는다.

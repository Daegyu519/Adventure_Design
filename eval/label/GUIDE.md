# T-16 라벨 지침

작성: 2026-11-10 · 연결: [docs/tasks.md](../../docs/tasks.md) T-16, [feedback-roadmap.md](../../docs/feedback-roadmap.md) §2 R-02

## 무엇을 판단하나

**상대의 실제 감정을 맞히는 것이 아니다.** "이 맥락에서 이 문장을 받으면, 보내기 전에 한 번 알려 줄 만큼 오해받을 수 있는가"를 판단한다.

- 감정 다섯 가지(차갑게·성의없게·화나게·무난하게·따뜻하게) 중 하나를 고르지 않는다.
- 같은 문장이라도 맥락이 다르면 답이 달라질 수 있다. 그게 이 세트의 목적이다.
- 정답은 없다. 각자 솔직하게 고르고, 서로 다르면 그 사례가 가장 쓸모 있다.

## 진행 순서

**링크 방식(2026-11-10, 권장):** 라벨 양식을 claude.ai 페이지로 올려 두었다(소유자 계정의 아티팩트, Share 메뉴로 조원에게 공유). 제출하면 페이지 저장소의 `labels/<라벨러 id>`에 저장되고, 저장 권한이 없는 사람(링크로 연 외부 사용자 등)에게는 제출 코드(JSON)가 떠서 메시지로 받는다. 라벨러끼리는 서로의 제출을 볼 수 없다. 문장 순서는 `export --seed 16`으로 만든 `eval/label/out/key.json`과 맞으므로, 합치기 전까지 다른 seed로 다시 export하지 않는다. 모인 제출은 `{labeler, labels}` 형식이라 아래 3번 `merge`에 그대로 넣는다.

1. **양식 만들기** (한 사람이 한 번):
   ```bash
   uv run --project engine python eval/label/label.py export --seed 16
   ```
   `eval/label/out/form.html`과 `key.json`이 생긴다. **`key.json`은 라벨이 끝날 때까지 아무에게도 보여 주지 않는다.** 양식은 한 번만 만들어 모두에게 **같은 `form.html`**을 보낸다(다시 만들면 순서가 바뀌어 합칠 수 없다).
2. **각자 라벨** (상의 금지): `form.html`을 브라우저로 열고 60개(30쌍)를 끝까지 고른 뒤 "저장"을 누른다. 이름 칸은 사람마다 다르게(겹치면 합치기가 멈춘다). `labels_<이름>.json`이 내려받아진다. 약 20~30분.
3. **합치기**:
   - **3명 이상(권장, 5명):** 다수결로 정한다. 상의할 필요가 없다.
     ```bash
     uv run --project engine python eval/label/label.py merge labels_*.json
     ```
     Fleiss kappa(여러 명 일치도), 두 사람씩 kappa 평균, 만장일치 수, **거의 갈림(5명 중 3:2)**·동표 목록, 사람별 경고 비율·다수결과 일치율이 나온다. 합의본은 `eval/contrast_set_t16.jsonl`, 자세한 보고서는 `eval/contrast_set_t16.report.json`. 동표(짝수 명이 반반)는 합의본에서 빠진다.
   - **2명:** `merge labels_A.json labels_B.json` → 일치율, Cohen's kappa, 불일치 목록. 불일치는 둘이 메모를 보고 상의해 정하고 `eval/contrast_set_t16.jsonl`에 직접 추가한다. **합의 전 일치율과 kappa를 먼저 기록**한다(합의 후 숫자는 의미가 없다).
4. **결과 읽기**:
   - kappa는 대략 0.6 이상이면 꽤 일치, 0.4 아래면 사람끼리도 많이 갈린다. **사람끼리의 일치도가 모델에 기대할 수 있는 천장이다.**
   - 거의 갈린 사례는 "판단 어려움" 후보다. 모델이 여기서 단정하면 안 된다(R-02).
   - 한 사람의 다수결 일치율이 유독 낮거나 경고 비율이 크게 다르면, 지침을 다르게 이해했는지 확인한다(그 사람을 빼지 말고 이유를 기록).

## 양식에서 고르는 법

양식의 두 버튼은 아래 뜻으로 읽는다(버튼 글자는 예전 것이라 다르게 적혀 있다).

| 버튼 | 이 지침에서의 뜻 |
|---|---|
| 차갑게 읽힘 | **알려 줄 만함** — 이 맥락에서 받는 사람이 서운하거나, 무시당했거나, 공격받았다고 느낄 가능성이 꽤 있다 |
| 괜찮음 | **알려 줄 필요 없음** — 짧거나 무뚝뚝해도 이 맥락에서는 자연스럽다 |

### 메모 칸 쓰는 법

"알려 줄 만함"을 골랐으면 메모를 꼭 쓴다. 아래 형식으로 짧게.

```
구절: <문제 되는 부분> / 읽힘: <어떻게 읽힐 수 있는지> / 맥락: <판단을 바꾼 상대 말>
```

예: `구절: ㅋㅋ / 읽힘: 슬픈 일을 웃어넘기는 듯 / 맥락: 할머니 돌아가심`

"괜찮음"이어도 헷갈렸으면 `애매: <이유>`라고 적는다. 애매한 사례는 R-02의 "판단 어려움" 기준을 만드는 데 쓴다.

## 판단 기준

### 알려 줄 만함으로 보는 경우

- 상대가 **감정을 드러냈는데**(힘듦, 기쁨, 사과, 부탁) 답이 그 감정을 무시하거나 끊는다.
- 상대의 **부탁·제안**에 이유나 대안 없이 잘라 말해, 거절 이상으로 상대를 무시하는 것처럼 읽힐 수 있다.
- 비꼬기, 따지기, 비속어가 상대를 향한다.

### 알려 줄 필요 없음으로 보는 경우

- 단순 확인·공지에 짧게 답했다(`ㅇㅇ`, `네.`, `알겠습니다.`).
- **정당한 거절·재촉·기한**이다. 단호하다는 것만으로는 경고 대상이 아니다. 예: 보안상 안 되는 일에 `안 돼요.`
- 친한 사이의 농담이나 장난이 맥락상 분명하다.
- 존댓말↔반말 차이만 있고 관계에 맞는다.

### 주의할 것

- **입력에 없는 사실을 지어내지 않는다.** "아마 둘이 싸운 사이일 것" 같은 추측으로 판단하지 않는다. 주어진 관계와 상대 말만 본다.
- **받는 사람 기준**으로 본다. 보내는 사람이 어떤 의도였을지는 생각하지 않는다.
- 맞춤법이나 문장 품질은 판단하지 않는다.
